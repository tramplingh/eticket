# E-Ticket Booking Platform

DBMS mini project. **MySQL 8** database with views, triggers and stored procedures; **FastAPI** backend that talks to MySQL in raw SQL (asyncmy, no ORM); **React + Vite + Tailwind** frontend.

```
backend/
  sql/
    01_schema.sql            9 tables, every key and constraint, indexes, app account
    02_programmability.sql   4 views, 8 triggers, 3 stored procedures
    03_seed.sql              demo data: 7 users, 4 venues, 508 seats, 10 events, 17 bookings
    04_queries.sql           the 14 synopsis operations as standalone SQL (re-runnable)
    upgrades/                only for a database created before 01_schema.sql existed
  app/                       FastAPI application (routers/, queries.py, database.py ...)
  scripts/create_admin.py    create or promote an admin account
frontend/                    React app
```

## 1. Database

Needs **MySQL 8.0.16 or newer** (CHECK constraints are enforced from 8.0.16).

### Fresh install (recommended)

In MySQL Workbench, connected as **root**, open and run each file in order (*File → Open SQL Script*, then the lightning-bolt button):

1. `backend/sql/01_schema.sql` (drops and recreates `eticket_booking`)
2. `backend/sql/02_programmability.sql`
3. `backend/sql/03_seed.sql`

Or from a terminal: `mysql -u root -p < backend/sql/01_schema.sql` and so on.

`01_schema.sql` also creates the app account `eticket_app@localhost` with the password `ChangeMe#2026` if it does not already exist. If it already exists, its password is left alone and it gains the `EXECUTE` grant the app now needs.

Run as root, in order: `upgrades/001_add_user_role.sql` (skip if you already ran it), `upgrades/002_ticket_cancel_and_integrity.sql`, then `02_programmability.sql`. Your existing database will not get the extra CHECK/UNIQUE constraints and indexes from `01_schema.sql`, so the fresh install is the better choice for marking.

## 2. Backend

```bash
cd backend
python -m venv venv
venv\Scripts\activate            # macOS/Linux: source venv/bin/activate
pip install -r requirements.txt
copy .env.example .env           # macOS/Linux: cp .env.example .env
uvicorn app.main:app --reload
```

In `.env`, set the `eticket_app` password inside `DATABASE_URL`. Special characters must be URL-encoded: `#` → `%23`, `@` → `%40`, `*` stays `*`. The seeded admin already exists; `python -m scripts.create_admin` is only needed for extra admins.

API docs: http://localhost:8000/docs

## DBMS concepts → where to point during the viva

**Relationships and cardinality** (`01_schema.sql`)
- 1:N: User–Booking, Venue–Seat, Venue–Event, Booking–Ticket: ordinary foreign keys.
- **1:1** Booking–Payment: a foreign key plus `UNIQUE (booking_id)` (`uq_payment_booking`). The UNIQUE is what makes it 1:1.
- **M:N** Event–Seat: resolved by the associative entity `event_seat`, with `UNIQUE (event_id, seat_id)`.
- Ticket–Event_Seat **N:1 over time**: a cancelled ticket keeps its row and the seat can be resold, but only one ticket may be live. MySQL has no partial unique index, so the generated column `live_seat_id` (NULL when cancelled) carries a UNIQUE index. Two live tickets for one seat are impossible even if the application has a bug.

**Attribute types**
- Composite: Name → `first_name` + `last_name`; Address → `street` + `city` + `state` (venue).
- Multivalued: phone → its own table `user_phone`, composite PK `(user_id, phone_number)`.
- Derived: `age` is computed in the view `v_user_profile` and never stored. `booking.total_amount` *is* stored for fast reads, so triggers keep it equal to the sum of live ticket prices (see the check query at the end of `04_queries.sql`).

**Constraints**: PRIMARY KEY, FOREIGN KEY with deliberate actions (CASCADE for owned rows like phones and seats; RESTRICT for history like bookings, tickets and payments), UNIQUE (email, venue+city, venue+date+time slot, seat position, QR code, transaction id), CHECK (prices ≥ 0, email shape, phone format, payment method), ENUM status domains, NOT NULL.

**Why triggers instead of CHECK for some rules**: a CHECK can only see the row being written and may not call `CURDATE()`. "Event date not in the past", "date of birth not in the future" and "seat belongs to the event's venue" (another table) are therefore BEFORE triggers.

**Normalisation**
- 1NF: no repeating groups. Phones moved out of `user`.
- 2NF: the only composite keys (`user_phone`, and the `event_seat` candidate key) have no partial dependencies. `price` depends on the whole (event, seat) pair.
- 3NF: no transitive dependencies. `city → state` is *not* a functional dependency (the same city name exists in different states, e.g. Aurangabad), so venue is in 3NF.
- Two intentional exceptions, both justified: `ticket.ticket_price` is a historical snapshot of the price at the time of sale, because the event price can change later; `booking.total_amount` is a derived value kept consistent by a trigger.

**Transactions and concurrency**
- `routers/bookings.py`, `create_booking`: `SELECT … FOR UPDATE` locks the seats in sorted order, then booking, tickets, seat status and payment commit together or roll back together. The test suite fires two simultaneous requests for the same seat; exactly one succeeds.
- `sp_cancel_ticket`: the transaction lives inside the procedure, with `EXIT HANDLER … ROLLBACK; RESIGNAL`.
- `database.py`, `transaction()`: BEGIN / COMMIT / ROLLBACK helper.

**Triggers** (`02_programmability.sql`)
- `trg_ticket_after_insert` / `trg_ticket_after_update`: maintain `booking.total_amount`. On cancellation they also put the seat back on sale, whichever path did the cancelling: app, procedure or a manual UPDATE.
- `trg_ticket_before_update`: ticket lifecycle. Only active → cancelled or active → used is allowed.
- `trg_event_before_insert/update`, `trg_user_before_insert/update`, `trg_event_seat_before_insert`: the rules CHECK cannot express.

**Stored procedures**: `sp_cancel_ticket` (used by the API), `sp_user_booking_history`, `sp_event_report`. Errors use `SIGNAL … MYSQL_ERRNO = 50000 + HTTP status`, and `main.py` turns them into 400/404/409 responses.

**Views**: `v_user_profile`, `v_event_availability`, `v_event_sales`, `v_booking_details` (an 8-table join). The reports API reads from them, so Workbench and the app always show the same numbers.

**Indexes**: on every lookup path (`event_date`, `event_type`, `(event_id, availability_status)`, `booking_date`, `(user_id, booking_date)`, `qr_code`). §13 of `04_queries.sql` shows with `EXPLAIN` why the date filter is written as a range instead of `DATE(booking_date) = …`.

**Security**: every value is a `%s` parameter, never formatted into SQL text; passwords are bcrypt hashes; the app connects as a least-privilege account (data rights + EXECUTE, no DDL).

### Naming differences from the synopsis diagram
- `seat.row_number` → `row_num`, because `ROW_NUMBER` is a reserved word in MySQL 8.
- Added columns: `user.role` (admin access), `user.created_at`, `ticket.live_seat_id` (generated, see above).
- Added `payment_status` value `partially_refunded`. Refunded amount = `payment.amount − booking.total_amount`.

## Roles

- **Customer**: browse and search events, book up to 10 seats, cancel one ticket or a whole booking before the event, manage profile and phone numbers.
- **Admin**: dashboard and reports, create/edit/delete events (only events with no bookings can be deleted), add venues and seat blocks, view all bookings or bookings by date, check tickets in at the gate. Every `/admin/*` and `/reports/*` endpoint returns 403 for non-admins.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `execute command denied … sp_cancel_ticket` | `GRANT EXECUTE ON eticket_booking.* TO 'eticket_app'@'localhost';` as root |
| `PROCEDURE eticket_booking.sp_cancel_ticket does not exist` | Run `02_programmability.sql` |
| `Access denied for user 'eticket_app'` | The password in `.env` doesn't match MySQL. Check that `#` is written as `%23` |
| Events page is empty | The seed dates have passed. Re-run 01 → 02 → 03 |
| `Check constraint … is violated` while editing in Workbench | Working as intended: that is the constraint doing its job |
